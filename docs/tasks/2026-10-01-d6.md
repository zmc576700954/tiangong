## 目标

为 BizGraph 主进程添加 OTLP/HTTP trace 导出能力，默认零开销（endpoint 未设置时 noop），覆盖以下观测点：

- `bizgraph.agent.start` / `bizgraph.agent.command` — AgentManager 入口与命令发送
- `bizgraph.subagent.invoke` — SubagentManager 子代理派发
- `bizgraph.mcp.connect` / `bizgraph.mcp.call` — MCP stdio 客户端
- `bizgraph.recipe.run` — Recipe runner
- `bizgraph.adapter.call{service, success}` — AdapterHealthMonitor 计数器（零持续时间 span）

边界（CLAUDE.md "Boundaries with Agent CLI"）：

- 不修改 Agent CLI 任何内部输入；
- 失败一律 best-effort，绝不向上抛；
- OTLP 导出失败静默吞掉，不阻塞主流程。

## 关键决策

### 1. 仅引入 trace SDK，不引 metrics / logs SDK

- spec 要求 `bizgraph.adapter.call{service, success}` 是 metric counter，但 metrics SDK 体积大，且 BizGraph 已经有 adapter-health-monitor 在做内存统计。
- 折中方案：用零持续时间的 span 当 counter，后端（Prometheus / Tempo）按 span count 聚合。
- 保持 `package.json` 体积不膨胀（metrics SDK 及其依赖合计 ~2MB）。

### 2. 初始化全部走动态 import

- `initTelemetry()` 内部 `import()` 包住 `sdk-node` / `otlp-http` / `resources` / `semantic-conventions`。
- 全部包在 try/catch 里，失败时静默吞掉，状态保持 `initialized=false`。
- 未提供 endpoint 时直接 return，不触发任何 import —— 真正的零开销。

### 3. 幂等 + retry

- `initPromise` 缓存 in-flight 初始化，并发调用复用同一 promise。
- 失败 / 完成后清空 `initPromise`，允许后续再次显式 init。
- `shutdownTelemetry` 自身幂等（多次调用 no-op）。

### 4. withSpan 模式

- `tracer.startActiveSpan(name, options, async fn)` 自动 set 当前 context，subagent / command / mcp / recipe 的 span 自然挂到 `agent.start` 下，形成完整调用链。
- 异常路径：`recordException(err)` + `setStatus(ERROR)` + rethrow，span end 后才抛，不掩盖原错误。

### 5. AdapterHealthMonitor 兜底

- `recordAdapterCall(...)` 用 try/catch 包住调用，监控路径永不抛错。
